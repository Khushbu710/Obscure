# Shared Data Models & Contracts

Owner: **Developer 2** maintains `packages/contracts/`. Developer 1 may propose changes via PR; no direct pushes to this package by either developer without the other's review (see change-approval process at the bottom).

Validation: all contracts are defined as **Zod schemas** in TypeScript (runtime validation, not just compile-time types), exported as both the schema and the inferred type, e.g. `export const MandateSchema = z.object({...}); export type Mandate = z.infer<typeof MandateSchema>;`. Every API boundary (frontend↔backend, backend↔signer) parses with `.parse()` and fails closed on mismatch.

Versioning: every top-level schema carries a `schemaVersion: number` field. Breaking changes bump the version and the old version's schema is kept in `packages/contracts/v{N}/` until both developers confirm migration — never silently mutate a shipped schema's meaning.

## 1. Mandate

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string (uuid) | yes | |
| `userId` | string | yes | single-user demo scope is fine; field exists for correctness |
| `status` | enum: `active, paused, revoked, expired` | yes | state machine, see below |
| `allowedCategories` | string[] | yes | e.g. `["esim"]` |
| `allowedMerchants` | string[] \| null | no | null = any merchant within category |
| `allowedProductIds` | string[] \| null | no | optional tightest restriction |
| `totalCapMinor` | integer | yes | **minor units (cents)**, never float |
| `perOrderCapMinor` | integer \| null | no | |
| `spentMinor` | integer | yes | authoritative running total, guardian-maintained |
| `currency` | string | yes | e.g. `"USD"` |
| `envelopeWalletRef` | string | yes | opaque reference to this mandate's independent `zcash-devtool` wallet instance (see `zcash-integration.md` §4) — **never a key** |
| `createdAt` / `expiresAt` | ISO8601 | yes | |
| `revokedAt` | ISO8601 \| null | no | |
| `schemaVersion` | integer | yes | starts at 1 |

State machine: `active -> paused -> active`, `active -> revoked` (terminal), `active -> expired` (terminal, time-based). The guardian must reject every order where `status != "active"`, with distinct rejection codes for `paused`, `revoked`, `expired`.

## 5. Guardian request / response

Request:
```json
{
  "mandateId": "m_123",
  "order": { "...Order fields above..." }
}
```
Response (approved):
```json
{
  "approved": true,
  "authorizationToken": "opaque, signed by guardian's own HMAC key, embeds orderId+nonce+mandateId+expiry(90s)",
  "checkedAt": "2026-11-04T10:00:00Z"
}
```
Response (rejected) — **always include an explicit code**, never a generic failure:
```json
{ "approved": false, "code": "BUDGET_EXCEEDED", "reason": "Order $14.00 exceeds remaining budget $9.50", "checkedAt": "..." }
```

Rejection codes (exhaustive, extend only by consensus — this list is also the attack-scoreboard's assertion surface): `CATEGORY_NOT_ALLOWED`, `MERCHANT_NOT_ALLOWED`, `PRODUCT_NOT_ALLOWED`, `PRICE_MISMATCH` (agent-reported price != freshly fetched price — allowed one re-proposal, see `bitrefill-integration.md` §3), `PER_ORDER_CAP_EXCEEDED`, `BUDGET_EXCEEDED`, `MANDATE_EXPIRED`, `MANDATE_PAUSED`, `MANDATE_REVOKED`, `NONCE_REUSED`, `MALFORMED_ORDER`.

`order.status` now follows the full state machine from `payment-flow.md` §1: `proposed, validated, reserved, authorized, signed, broadcast, mined, confirmed, settlement_pending, delivered, failed, payment_uncertain, refund_pending, refunded, rejected, expired, cancelled`.

## 6. Authorization request / signer response

Request to signer (internal network only, HMAC-authenticated, never reachable from the frontend or the agent directly):
```json
{ "authorizationToken": "...", "order": { "...": "..." } }
```
Signer independently re-derives its own verdict — it does **not** trust the guardian's `approved:true` at face value; see `security-architecture.md` §3. Response:
```json
{ "signed": true, "txProposal": { "...": "..." }, "signedAt": "..." }
```
or
```json
{ "signed": false, "code": "NONCE_ALREADY_CONSUMED", "reason": "..." }
```

## 8. Blockchain transaction request / status

Owner: Dev 1 (this is the wrapper service's own internal contract, shared because the signer calls it).

```json
{ "walletRef": "wallet:m_8f2a", "outputs": [{ "address": "utest1...", "amountZatoshi": 1500000 }], "memo": null }
```
Status enum: `pending, broadcast, mined, confirmed(N confirmations), failed` — matches `payment-flow.md` §1's seen/mined/confirmed distinction, required by the builder pack.

## 9. Receipt

| Field | Type | Notes |
|---|---|---|
| `receiptId` | string | |
| `orderId` | string | |
| `commitment` | string (hex) | `SHA-256(orderId ‖ priceMinor ‖ merchantId ‖ timestamp ‖ salt)` — see `payment-flow.md` §6 |
| `salt` | string | stored encrypted, released only on selective disclosure |
| `signature` | string | Ed25519 signature over `commitment` by the receipt service's key |
| `encryptedPayload` | string | full purchase detail, encrypted at rest |
| `createdAt` | ISO8601 | |

Explicitly: this is a **digital signature + hash commitment**, not a zero-knowledge proof. Selective disclosure = revealing `salt` + the underlying fields for one `commitment`, which lets a verifier recompute and check the hash and signature without seeing any other receipt.

## Change approval process for `packages/contracts/`

1. Either developer opens a PR touching only files under `packages/contracts/`.
2. The PR description must state: which consumers (frontend, backend, signer) are affected, and whether it's additive (safe) or breaking (requires version bump).
3. Dev 2 (maintainer) reviews and merges; Dev 1 reviews when the change affects frontend-consumed shapes.
4. No one edits a contract file as a side-effect of an unrelated feature PR — contract changes are always their own PR.
